# AMA Assessment — Discover before you modernize (the HOW layer)

This skill is the **HOW** behind the *Discover* phase of the IBM Java modernization story:
**Discover with AMA → Modernize with Bob → Run on Liberty.** It is invoked by the
`ibm-presales-java-modernization` mode at its Phase 0 AMA Assessment Gate, and it feeds the
`java-app-modernization` skill (the assessment becomes that skill's Phase 1 input).

It tells you exactly how to run the AMA Discovery Tool, ingest real AMA artifacts, drive the
AMA product UI, and — for demos with no live AMA — generate a synthetic AMA-style assessment
that is clearly labeled illustrative. Most importantly, it keeps the **AMA↔Bob boundary
honest** so Bob never over-claims.

> **Golden rule (AMA changes per release; this is verified against the mode's product
> knowledge for AMA 4.5.x, not a live install in this environment).** Before asserting a
> flag, artifact name, or UI path, verify against the live tool: `ama-discovery --help`,
> the AMA product UI, and IBM's official AMA documentation. Treat version-specific details
> (CLI flags, podman compatibility, default ports) as approximate until checked. Confirm
> the installed version from the Discovery Tool bundle / product "About" screen.

## 1. Mental model — AMA is TWO tools and THREE artifacts (never blur them)

Over-claiming here is the #1 credibility risk. Internalize this split:

| # | Thing | What it is | Can Bob do it? |
|---|-------|-----------|----------------|
| **Tool 1** | **Discovery Tool** (`ama-discovery`) | A self-contained CLI with its own bundled JRE. Scans a source app server **or a WAR/EAR binary** and emits a **data collection**. Raw facts only — **no effort, no recommendation.** Deterministic. | ✅ **Bob CAN run it.** |
| **Tool 2** | **AMA local product** | Containerized (podman/docker), UI on `https://localhost:443` (and `:3000`). Ingests a data collection → produces **Visualization + Assessment + Migration Plan**. The assessment **engine**; review is **human-in-the-loop on purpose** — that screen IS the demo value. | ❌ **Bob does NOT replace it.** Bob guides/ingests. |
| **Artifact A** | **Data collection** (`profile.zip` / `Dmgr01.zip`) | Output of Tool 1. Contains the **Inventory / Technology / Analysis** reports (html + json). Facts, not a plan. | ✅ Bob runs Tool 1 to make it; ✅ Bob reads it. |
| **Artifact B** | **Assessment** (in the product UI / exports) | Target recommendation per app, **complexity tier** (Simple/Moderate/Complex), **developer-days**, **unique vs common** code split, per-app challenges. | ❌ Generated by Tool 2 (human-reviewed). ✅ Bob ingests exports. |
| **Artifact C** | **Migration Plan** (`*_migrationPlan.zip`) | The deliverable that feeds Bob's loop and ships in the **Premium Package**: a Liberty `server.xml`, a `Containerfile`, Kubernetes `*.yaml` (+ `secret.yaml`), `pom.xml`, and the reports. | ❌ Bob does **not** manufacture a genuine one. ✅ Bob **ingests** it. (For demos Bob may generate a *synthetic AMA-style* assessment — labeled illustrative.) |

**The honesty boundary — say it when relevant, verbatim:**
> *Bob runs the Discovery Tool and applies AMA's plan. The assessment, visualization, and
> migration-plan generation are the AMA product, shown and human-reviewed. They are
> complementary — and the AMA↔Bob integration is the differentiator vs a generic AI
> assistant.* **Never claim "Bob ran the AMA assessment."**

AMA migrates from these sources: **WebSphere Application Server (traditional), JBoss,
WebLogic, and Tomcat.** It ships **AMA Developer Tools** (Eclipse-based) for deeper
code-level work. AMA automates up to **70%** of analysis/planning/migration steps and saves
up to **95%** of discovery & assessment effort (cite as IBM-published figures, not
guarantees).

## 2. The Phase 0 decision — pick the branch, then act

The mode asks one gate question first: *"What IBM AMA assessment input do you have?"* This
skill is the HOW for each answer. **The assessment FEEDS the rest of intake — produce/ingest
it BEFORE the target-runtime question** so the Liberty-vs-(MoRE/Quarkus/stay) recommendation,
the complexity tier, the dev-days, and the islands sequencing come from AMA **as evidence.**

| Branch | User has… | What this skill does |
|--------|-----------|----------------------|
| **A** | A **migration plan** (`*_migrationPlan.zip`) and/or exported reports | **§5 Ingest.** Parse issues, tiers, dev-days, unique-vs-common, and the AMA `server.xml`/`Containerfile`/k8s YAML. The real Premium-Package path — narrate the provenance. |
| **B** | A **data collection** (`profile.zip`/`Dmgr01.zip`), not yet assessed | **§4.4 Read it.** If the AMA product is available → **§4 guide upload→assess**; else summarize the collection and fall back to **§6 synthetic**. |
| **C** | No assessment yet, but AMA **installed** | **§3 Run the Discovery Tool** (prefer the WAR/EAR **binary scan** — air-gapped, no live server), then → branch B. |
| **D** | **No AMA** — generate a synthetic AMA-style assessment (demo default) | **§6 Synthetic.** Produce `MODERNIZATION_ASSESSMENT.md`, present it as an explicit, narrated *Discover* phase, clearly labeled illustrative. |
| **E** | Continue **without** an AMA assessment | First state plainly what is lost (target rationale, effort/risk, unique-vs-common, islands sequencing), **then** proceed. Do not skip silently. |

## 3. Run the Discovery Tool (`ama-discovery`) — Tool 1

The Discovery Tool is a standalone CLI with a bundled JRE; it does **not** need the AMA
product running. It produces a **data collection** (Artifact A) — facts only.

### 3.1 Two scan modes

```bash
# (A) BINARY scan — preferred for demos / air-gapped / when no live server is reachable.
#     Scans a built artifact directly. No running app server required.
./bin/ama-discovery -o <path/to/app.war>      # or app.ear

# (B) LIVE-SERVER scan — richest facts; needs access to the source server install.
#     tWAS example (point at the WAS install + profile):
./bin/ama-discovery -w <WAS_HOME> -p <PROFILE_NAME>
```
- **Prefer the binary scan** (`-o`) when the goal is speed, repeatability, or an air-gapped
  demo — it is deterministic and needs no live topology.
- Use the live-server scan when you need datasource/JNDI/queue wiring and shared-resource
  facts that only the running configuration carries.
- Flags vary by AMA version and source platform (WebLogic/JBoss/Tomcat have their own
  options). **Always run `./bin/ama-discovery --help` first** and match the source platform.

### 3.2 Output — the data collection

The run emits a **data collection** zip (commonly `profile.zip`, or `Dmgr01.zip` for a WAS
Deployment Manager) containing three reports as **html + json**:

| Report | Answers | Bob uses it for |
|--------|---------|-----------------|
| **Inventory** | *What exists* — apps, modules, libraries, descriptors | Estate list, per-app module map |
| **Technology** | *Which frameworks/versions/APIs* | Detect Jakarta vs javax, proprietary APIs, removed-JDK-module use |
| **Analysis** | *Issues & remediation hints* | Seed the Phase 1 bucket list in `java-app-modernization` |

Read the **json** variants programmatically; show the **html** to the human. Then go to
branch B (assess in the product, or synthesize §6).

## 4. Drive the AMA product (Tool 2) — Visualization → Assessment → Migration Plan

This is the human-in-the-loop engine. **Bob guides; the human reviews and decides.** Bob does
not generate the genuine assessment or plan.

### 4.1 Start the product

```bash
./launch.sh                 # Linux/macOS   (Windows: .\launch.bat)
# UI: https://localhost:443   (a secondary UI surface may run on :3000)
```
- **Podman compatibility (AMA 4.5.x on macOS):** AMA 4.5.x does **not** support
  Podman ≥ 5.6.0 — **pin Podman to 5.5.x**. (Verify against current AMA release notes.)
- Resource footprint and exact tags are version-specific — check the AMA install guide.

### 4.2 Workspace lifecycle (narrate each step in a demo)

```
Create workspace
  → Upload results          (the Dmgr01.zip / profile.zip data collection from §3)
  → Manage destination      (pick the target runtime context)
  → Visualization           (estate map: apps ↔ databases ↔ queues; "islands" highlighted)
  → Assessment              (per-app complexity Simple/Moderate/Complex; dev-days; unique vs common)
  → Download migration plan (server.xml + Containerfile + k8s *.yaml + pom.xml + reports)
```

### 4.3 The three product stages — what each delivers

1. **Visualization** — discovers the estate, maps application dependencies to databases and
   queues, and identifies standalone **"islands"** (safe places to start). *This screen is
   the "Discover with clarity" wow moment — let it breathe in the demo.*
2. **Assessment** — recommends the best modernization target (overall and per app), scores
   **complexity** (Simple = no code changes · Moderate = well-understood remediation ·
   Complex = deeper rework), separates **unique** vs **common** code (common = fix once,
   apply to many apps), and estimates effort in **developer-days**. Reports: **Inventory,
   Technology, Analysis.**
3. **Migration Plan** — generates a Liberty configuration derived from existing config plus
   deployment assets: `server.xml`, `Containerfile`, Kubernetes `*.yaml` + `secret.yaml`,
   and `pom.xml`. This is Artifact C — the thing Bob ingests next.

### 4.4 If you only have a data collection (branch B) and no product

Summarize the Inventory/Technology/Analysis json into an estate table and a per-app issue
list, then **fall back to a synthetic AMA-style assessment (§6)** for the recommendation,
clearly stating it is synthesized from facts, not a product-generated assessment.

## 5. Ingest a real migration plan / reports (branch A) — feed Bob's loop

When the user has a genuine `*_migrationPlan.zip` (Premium Package) or exported reports,
**narrate the provenance** ("this is the AMA product's own plan") and parse it.

### 5.1 What's inside `*_migrationPlan.zip`

```
<plan>_migrationPlan.zip
├── server.xml                 # Liberty config AMA derived from the source config
├── Containerfile              # UBI + Liberty image build for the app
├── <app>.yaml / deployment    # Kubernetes manifests (+ secret.yaml placeholders)
├── pom.xml                    # build wiring for the target
└── reports/                   # Inventory / Technology / Analysis (html + json)
    └── tWAS/details/applications/...   # per-app HTML/PDF (Rule Severity Summary, recipe list)
```

### 5.2 Parse into a Bob-ready work plan

Extract and hand off to `java-app-modernization` (its Phase 1):

| From the plan | Pull out | Hands off to |
|---------------|----------|--------------|
| Analysis report | Issue list with **severity** (Critical/Warning/Info) | Phase 1 bucketing (Automated / Self-directed / Informational) |
| Assessment | **complexity tier**, **developer-days**, **unique vs common** split | Sequencing + effort narrative |
| Visualization | App↔DB↔queue map, **islands** | "Islands first" extraction order |
| `server.xml` | Liberty features the app needs | `modern/` server config baseline |
| `Containerfile` / k8s | Deploy target shape | Phase 5/deploy artifacts |

**Do not invent issues the report didn't flag, and do not guess deprecated-API
replacements** — verify against vendor docs. The AMA findings are the contract.

## 6. Generate a SYNTHETIC AMA-style assessment (branch D — the demo default)

When there is no live AMA, produce a realistic, clearly-labeled `MODERNIZATION_ASSESSMENT.md`
and present it as an explicit, narrated **Discover** phase. **Every number is synthetic and
labeled "illustrative."** Use fictional companies (NovaTech, Apex, BlueLine, Meridian) and
`@example.com` — never real client data (see the confidentiality policy in the mode).

### 6.1 Template

```markdown
# Modernization Assessment — {DEMO-CODE}  ·  AMA-style (SYNTHETIC, ILLUSTRATIVE)
> Demonstration artifact. Estate, dependencies, complexity tiers, and developer-day
> estimates are synthetic and illustrative — not a product-generated AMA assessment.

## 1. Estate overview
Synthetic portfolio of {20–30} apps on {tWAS | WebLogic | Tomcat | JBoss | mixed}.
| Source runtime | # apps | Java level | Notes |
|---|---|---|---|
| tWAS 9.0.5 | 14 | 8 | javax.*; some com.ibm.websphere.* APIs |
| Tomcat 9   | 8  | 8/11 | servlet apps, no EJB |
| ...        | .. | ..  | ... |

## 2. Dependency map (apps ↔ databases ↔ queues)  — ISLANDS highlighted
- 🟢 **Islands (start here):** ORDERS-UI, CATALOG-SVC  (no shared DB/queue)
- 🟡 Shared DB cluster: BILLING + INVOICES (same Oracle schema) → migrate same wave
- 🔴 Hub: CORE-LEDGER (8 inbound deps) → migrate last

## 3. Per-app assessment
| App | Source | Target | Complexity | Dev-days | Unique vs Common | Top issues | #deps |
|---|---|---|---|---|---|---|---|
| ORDERS-UI | tWAS 9 | Liberty | Simple | 3 | 2 / 1 | javax→jakarta only | 1 |
| BILLING   | tWAS 9 | Liberty | Moderate | 9 | 6 / 3 | JAXB removed, WAS SSO API | 4 |
| CORE-LEDGER | WebLogic | Liberty | Complex | 22 | 18 / 4 | weblogic.* APIs, Struts 1 | 8 |

## 4. Reports (summarized)
- **Inventory** — what exists (apps, modules, libraries, descriptors).
- **Technology** — frameworks/versions/APIs (Jakarta vs javax, removed JDK modules).
- **Analysis** — issues & remediation (Critical N · Warning N · Info N).

## 5. Recommended target & sequence
- Target rationale per app (Liberty default; MoRE if ops must not change; Quarkus greenfield).
- **Sequence:** islands first → Moderate next → Complex last (land-and-expand).
- Complexity model: Simple (no code change) · Moderate (well-understood remediation) · Complex (deeper rework).
```

### 6.2 Make it credible
- Keep the runtime distribution, dependency map, and dev-days internally consistent (an
  island with 1 dependency should not be "Complex").
- Mark **common code** items explicitly — "fix once, applies to N apps" is a core AMA value.
- Tie the target recommendation to the complexity tier and the islands map, not to preference.

## 7. Critical constraints (these protect credibility)

- ✅ **Never claim "Bob ran the AMA assessment."** Bob runs the *Discovery Tool* and
  *ingests* the plan; the **assessment/visualization/migration-plan are the AMA product**,
  human-reviewed. State the boundary whenever AMA capabilities come up.
- ✅ **Discovery Tool = facts only.** It does not produce effort or a recommendation — that's
  Tool 2. Don't present Discovery output as an assessment.
- ✅ **Synthetic ≠ real.** A generated assessment (§6) must be labeled illustrative in the
  doc and out loud. Never present it as a product-generated plan.
- ✅ **Prefer the binary scan** (`-o`) for air-gapped/demo discovery; live-server scan when
  you need wiring facts.
- ✅ **Podman 5.5.x pin** for AMA 4.5.x on macOS (verify per release).
- ✅ **No real client data.** Discovery inputs from a real estate must be anonymized *before*
  any LLM/AI processing (see `java-app-modernization` Anonymization Policy). Demos use
  synthetic estates only.
- ✅ **Verify-live** any flag/port/artifact name before asserting it (golden rule).

## 8. Troubleshooting

| Symptom | Likely cause → fix |
|---------|--------------------|
| `ama-discovery` flag rejected | Version/platform drift. `./bin/ama-discovery --help`; match source platform (WAS/WebLogic/JBoss/Tomcat). |
| Discovery emits little/no data on binary scan | WAR/EAR missing descriptors, or wrong artifact. Try the live-server scan (`-w`/`-p`) for full wiring facts. |
| AMA product won't start on macOS | Podman ≥ 5.6.0 with AMA 4.5.x. Pin Podman to 5.5.x. |
| UI not reachable | Wrong port/scheme — it's **https**://localhost:443 (and possibly :3000). Check `launch.sh` logs. |
| "Where's the recommendation?" after discovery | You only ran Tool 1 (facts). Upload the data collection to Tool 2 (§4) or synthesize (§6). |
| Plan ingested but issues look invented | You added findings not in the Analysis report. Stick to the report; flag extras as "Bob-observed," separately. |

## 9. Hand-off — where the assessment goes next

- **To `java-app-modernization`:** the parsed issues/tiers/islands become its **Phase 1**
  input (bucketing + sequencing). The plan's `server.xml`/`Containerfile`/k8s seed its
  target config and deploy artifacts.
- **To `java-monolith-decomposition`:** the Visualization islands and app↔DB↔queue map are
  the starting seams for extraction sequencing.
- **To the `ibm-presales-java-modernization` mode:** the target recommendation, complexity
  tier, dev-days, and islands feed the Modernization Demo Brief (so intake is evidence-led,
  not asked cold).
